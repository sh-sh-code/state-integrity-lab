# State Integrity Lab

**State Integrity Lab (SIL)** is a defensive QA / audit toolkit for verifying
that AI / SaaS services correctly converge on their post-transition state after
events such as:

- Deletion (files, project knowledge, accounts)
- Permission downgrades or removals
- OAuth / connector revocation
- Workspace / team membership changes
- API key rotation

When these transitions happen, the system has to update many surfaces — UI,
search index, retrieval / RAG layer, history, exports, notifications, caches,
and logs. SIL helps an authorized operator (you, on your own data, in scope)
record observations *before* and *after* the transition, re-observe later to
catch cache lag, diff the artifacts, and produce a Bug-Bounty / QA / audit
ready Markdown report.

## Purpose

The goal is to surface **state inconsistency** and **unexpected data
persistence** — for example:

- A file deleted from the UI still appears in an export 24 hours later.
- An OAuth connector revoke leaves connector-derived content in search.
- A user downgraded from admin still sees admin-only IDs in error pages.
- A rotated API key's old prefix still appears in a dashboard.

This is **not** an attack tool. SIL never attempts to break authentication,
bypass rate limits, exfiltrate other people's data, or create load.

## Legal & scope

Read [`docs/legal_and_scope.md`](docs/legal_and_scope.md) **before** running
SIL against any third-party service.

In short:

- Use SIL **only** on your own account and your own test data, or within an
  explicitly authorized Bug Bounty / audit scope.
- Always read the program's policy and scope first.
- **Never** attempt: authentication bypass, credential brute force, rate-limit
  evasion, denial-of-service, high-load testing, or accessing other people's
  data.
- When you find an issue, keep evidence minimal and redact sensitive values
  before reporting.

If a target service is **not** in a permitted scope, do not run SIL against it.

## Setup

```bash
# Python 3.11+ recommended
python -m venv .venv
source .venv/bin/activate
pip install -e .[dev]

# Optional — copy the env template
cp .env.example .env

# Initialize the SQLite DB and artifact / report directories
sil init
```

## Basic commands

```bash
# 1. List built-in scenario templates
sil scenario templates

# 2. Create a scenario from a template
sil scenario create \
    --name "my-drive-revoke-2026-05-08" \
    --target-service "example.com" \
    --template connector_revoke_persistence

# 3. Record a "before" observation (e.g. a search result you captured)
sil observe html --scenario 1 --phase before --file ./before-search.html \
    --note "Search for 'connector-only-keyword' returns 3 hits"

# 4. Mark the transition you performed (the human did this, not the tool)
sil transition mark --scenario 1 --type revoked_oauth \
    --note "Revoked Drive connector at 14:02 UTC"

# 5. Record an "after" observation
sil observe html --scenario 1 --phase after --file ./after-search.html \
    --note "Same search, immediately after revoke"

# 6. Diff the two observations and detect persistence
sil diff --before 1 --after 2 \
    --keyword "connector-only-keyword"

# 7. Schedule delayed re-observations (Phase 1 only records the schedule)
sil schedule --scenario 1 --in 5m --in 1h --in 24h

# 8. Generate a Markdown report (with redaction by default)
sil report generate --scenario 1
```

## Sample scenarios (built-in templates)

| Key                            | Hypothesis                                                                 |
|--------------------------------|----------------------------------------------------------------------------|
| `connector_revoke_persistence` | After OAuth revoke, connector-sourced content disappears from all surfaces |
| `project_knowledge_deletion`   | Deleted knowledge items are unrecoverable via UI / search / export         |
| `team_permission_downgrade`    | Downgraded members lose all admin-only views and IDs                       |
| `api_key_rotation_persistence` | Old key prefix disappears from dashboards, logs, webhooks                  |
| `export_after_deletion`        | Exports made after deletion never contain the deleted item                 |
| `delayed_cache_inconsistency`  | Caches converge on the post-transition state within the documented SLA     |

Run `sil scenario templates` to see the full list and hypotheses.

## Do not do this

- Do not run SIL against a service you do not own and is not in a permitted
  scope.
- Do not collect, store, or include in reports any data that belongs to other
  users.
- Do not bypass authentication, MFA, or rate limits — even to "make the test
  easier".
- Do not generate unusual load (high-rate scraping, parallel browsers, DoS).
- Do not store live secrets in artifacts. Rotate any captured token before
  committing.
- Do not share screenshots / HTML snapshots that contain other users' data,
  even after redaction — when in doubt, do not share.

## What's in Phase 1

- Project skeleton, packaging, env config
- SQLite DB + ORM models (Scenario / Observation / Transition / DiffResult /
  Report / DelayedCheck)
- Typer CLI: `init`, `scenario create|list|templates`, `observe
  manual|screenshot|html|json|api`, `transition mark|list`, `diff`, `schedule`,
  `report generate`
- Manual / JSON / HTML / screenshot observation capture (operator-supplied
  artifacts only)
- Text / JSON / screenshot diff with persistence heuristics
- Delayed-check **scheduling** (rows only — no background runner yet)
- Markdown report generator with secret redaction
- Documentation and pytest unit tests

## What is deliberately **not** in Phase 1

These are reserved for Phase 2+:

- Playwright-driven, logged-in browser observation
- Perceptual screenshot diff (Pillow / ImageChops based)
- Background runner that actually executes scheduled delayed checks
- Service-specific authenticated API observation templates
- Export-bundle (zip / tar) comparison helpers
- Severity-hint scoring improvements
