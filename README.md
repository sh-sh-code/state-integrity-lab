# State Integrity Lab

**State Integrity Lab (SIL)** is a defensive QA / audit toolkit for verifying
that AI / SaaS services correctly converge on their post-transition state after
events such as:

- Deletion (files, project knowledge, accounts)
- Permission downgrades or removals
- OAuth / connector revocation
- Workspace / team membership changes
- API key rotation

When these transitions happen, the system has to update many surfaces — UI,
search index, retrieval / RAG layer, history, exports, notifications, caches,
and logs. SIL helps an authorized operator (you, on your own data, in scope)
record observations *before* and *after* the transition, re-observe later to
catch cache lag, diff the artifacts, and produce a Bug-Bounty / QA / audit
ready Markdown report.

## Purpose

The goal is to surface **state inconsistency** and **unexpected data
persistence** — for example:

- A file deleted from the UI still appears in an export 24 hours later.
- An OAuth connector revoke leaves connector-derived content in search.
- A user downgraded from admin still sees admin-only IDs in error pages.
- A rotated API key's old prefix still appears in a dashboard.

This is **not** an attack tool. SIL never attempts to break authentication,
bypass rate limits, exfiltrate other people's data, or create load.

## Legal & scope

Read [`docs/legal_and_scope.md`](docs/legal_and_scope.md) **before** running
SIL against any third-party service.

In short:

- Use SIL **only** on your own account and your own test data, or within an
  explicitly authorized Bug Bounty / audit scope.
- Always read the program's policy and scope first.
- **Never** attempt: authentication bypass, credential brute force, rate-limit
  evasion, denial-of-service, high-load testing, or accessing other people's
  data.
- When you find an issue, keep evidence minimal and redact sensitive values
  before reporting.

If a target service is **not** in a permitted scope, do not run SIL against it.

## Setup

```bash
# Python 3.11+ recommended
python -m venv .venv
source .venv/bin/activate
pip install -e .[dev]

# Optional — copy the env template
cp .env.example .env

# Initialize the SQLite DB and artifact / report directories
sil init
```

## Basic commands

```bash
# 1. List built-in scenario templates
sil scenario templates

# 2. Create a scenario from a template
sil scenario create \
    --name "my-drive-revoke-2026-05-08" \
    --target-service "example.com" \
    --template connector_revoke_persistence

# 3. Record a "before" observation (e.g. a search result you captured)
sil observe html --scenario 1 --phase before --file ./before-search.html \
    --note "Search for 'connector-only-keyword' returns 3 hits"

# 4. Mark the transition you performed (the human did this, not the tool)
sil transition mark --scenario 1 --type revoked_oauth \
    --note "Revoked Drive connector at 14:02 UTC"

# 5. Record an "after" observation
sil observe html --scenario 1 --phase after --file ./after-search.html \
    --note "Same search, immediately after revoke"

# 6. Diff the two observations and detect persistence
sil diff --before 1 --after 2 \
    --keyword "connector-only-keyword"

# 7. Schedule delayed re-observations (Phase 1 only records the schedule)
sil schedule --scenario 1 --in 5m --in 1h --in 24h

# 8. Generate a Markdown report (with redaction by default)
sil report generate --scenario 1
```

## Sample scenarios (built-in templates)

| Key                            | Hypothesis                                                                 |
|--------------------------------|----------------------------------------------------------------------------|
| `connector_revoke_persistence` | After OAuth revoke, connector-sourced content disappears from all surfaces |
| `project_knowledge_deletion`   | Deleted knowledge items are unrecoverable via UI / search / export         |
| `team_permission_downgrade`    | Downgraded members lose all admin-only views and IDs                       |
| `api_key_rotation_persistence` | Old key prefix disappears from dashboards, logs, webhooks                  |
| `export_after_deletion`        | Exports made after deletion never contain the deleted item                 |
| `delayed_cache_inconsistency`  | Caches converge on the post-transition state within the documented SLA     |

Run `sil scenario templates` to see the full list and hypotheses.

## Do not do this

- Do not run SIL against a service you do not own and is not in a permitted
  scope.
- Do not collect, store, or include in reports any data that belongs to other
  users.
- Do not bypass authentication, MFA, or rate limits — even to "make the test
  easier".
- Do not generate unusual load (high-rate scraping, parallel browsers, DoS).
- Do not store live secrets in artifacts. Rotate any captured token before
  committing.
- Do not share screenshots / HTML snapshots that contain other users' data,
  even after redaction — when in doubt, do not share.

## What's new in Phase 2

- **Playwright observer** (`sil observe playwright`). Loads a logged-in
  profile via `--storage-state` (the operator exports it ahead of time);
  SIL never performs logins itself. Captures screenshot + DOM in one shot.
- **Perceptual screenshot diff** using Pillow + ImageChops. Reports the
  fraction of differing pixels, writes a diff image, and supports
  `--ignore-region x,y,w,h` masks for dynamic UI elements. Severity is now
  derived from the differing-pixel ratio.
- **Bundle diff** (`sil bundle diff --before before.zip --after after.zip
  --keyword foo`). Compares two export archives (zip/tar/tar.gz), runs
  per-member text/JSON/byte diffs, and applies the keyword-persistence rule
  to the AFTER bundle.
- **API templates** (`sil observe api-template`). Each template declares an
  `allowed_endpoints` allow-list, reads its token from a specific env var
  only, enforces a minimum inter-request delay (≥1s), and refuses to run
  without `--max-requests`. Tokens never appear in logs or artifacts.
- **Delayed-check runner** (`sil scheduler run-due`). Walks due
  `delayed_checks` rows and prints the prescription for the operator —
  the runner does NOT perform observations itself. `sil scheduler
  mark-done --check <id>` records that the operator has acted.
- **Weighted severity scoring** for persistence findings (see
  `docs/methodology.md`).
- **Lint/CI**: ruff + mypy + pytest matrix on Python 3.11/3.12 via GitHub
  Actions.

## What's new in Phase 1.5

Phase 1.5 is a documentation + reporting hardening pass aimed at making SIL
usable for real Bug Bounty / QA submissions.

- **Six fully-fleshed scenario playbooks** with prerequisites, reportable
  conditions, false-positive traps, prohibited actions, and recommended
  fix direction. Render any of them with
  `sil scenario show-template <key>`.
- **`sil scenario list-templates` / `show-template <key>`** for fast
  introspection from the terminal.
- **`sil scenario annotate`** attaches Bug-Bounty-grade prose to a
  scenario (scope & authorization, test data, expected, actual, security
  impact, limitations, recommended fix). `sil scenario show-metadata`
  prints what's currently attached.
- **Eight new report sections** rendered by `sil report generate`: Scope &
  Authorization, Test Data Used, Timeline (auto-built from observations,
  transitions, diffs, and delayed checks), Expected vs Actual, Security
  Impact, Evidence (artifact paths grouped by phase), Limitations,
  Recommended Fix Direction. Sections fall back to a clear "to be filled
  in by operator" placeholder if not yet annotated.
- **Operator-facing docs** in `docs/`:
  [`methodology.md`](docs/methodology.md),
  [`scenario_playbook.md`](docs/scenario_playbook.md),
  [`report_quality.md`](docs/report_quality.md).
- **`sil scenario export`** packs a scenario into a single zip
  (`manifest.json` + `report.md` + `artifacts/<rel>/...`) for hand-off
  to Bug Bounty triage or to another operator. The manifest carries
  SHA-256 of every member so reviewers can detect tampering. Default
  is `--redact`, and the exporter refuses to include
  `storage_state.json` or write the bundle inside `artifacts/`.
- **`sil init --wizard`** walks a first-time operator through choosing
  a template, recording the scope source (BB program URL / sandbox /
  QA charter), generating a `SIL-PROBE-<rand>` signature, and
  scheduling 5m / 1h / 24h re-observation prompts — all in a single
  sub-minute interactive flow. The wizard never makes network
  requests, never asks for credentials, and never logs in; it only
  creates DB rows.
- **Findings registry** (`sil finding open/list/show/update`) tracks
  operator-curated findings through the full triage lifecycle
  (`open / submitted / needs_more_info / accepted / fixed / wont_fix
  / duplicate`), with severity, external program id, linked diff ids,
  and optional bounty payout fields. Findings are rendered into the
  report's new "Findings" section (highest severity first) and
  included verbatim in `sil scenario export` manifests.

### Pre-flight checklist before testing a real service

Run through this list every time before pointing SIL at a service that
isn't a sandbox you fully own:

- [ ] You have re-read the program's scope statement (private brief if
      Bug Bounty; QA charter if internal).
- [ ] The endpoints you will observe are explicitly in scope.
- [ ] Every account you will use is yours (or your team's authorized
      test account). No friend's accounts. No customer accounts.
- [ ] You have run `sil scenario show-template <key>` and read the
      "Prohibited actions" list out loud.
- [ ] The data you will plant has a unique signature you control (e.g.
      `SIL-PROBE-{rand}`), so the diff catches the right thing.
- [ ] The Playwright `storage_state.json` (if used) was exported on a
      machine you own and is stored in an encrypted volume.
- [ ] You have set `SIL_REDACT_BY_DEFAULT=true` and re-read the redaction
      patterns. You will manually scrub anything domain-specific.
- [ ] You have not stored any live secret in any SIL artifact.
- [ ] You have decided in advance what you would NOT report (informative
      only) so the run produces a focused submission rather than a
      laundry list.
- [ ] The first run is on a freshly created tenant / project / account so
      the state you capture is reproducible.

### Optional Playwright dependency

```bash
pip install -e .[playwright]
playwright install chromium
```

Then export an existing logged-in browser profile to a JSON file your
operator owns, e.g.:

```python
# Run this once, manually, on a machine where you are logged in to YOUR account.
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    b = p.chromium.launch(headless=False)
    ctx = b.new_context()
    page = ctx.new_page()
    page.goto("https://example.com/login")
    input("Log in manually, then press Enter to save state...")
    ctx.storage_state(path="storage_state.json")
```

Use that file with `sil observe playwright --storage-state ./storage_state.json`.

### Scheduling delayed re-observation prompts

Add a single cron entry like:

```cron
*/5 * * * * cd /path/to/state-integrity-lab && /path/to/.venv/bin/sil scheduler run-due >> ~/.sil-runner.log 2>&1
```

The runner only prints prescriptions; it never runs observations on its own.

## What is deliberately **still not** automated

These are intentionally left to the operator:

- Logging in to third-party services. SIL refuses to.
- Crawling. The Playwright observer captures one URL per call.
- Bypassing rate limits, retrying around 429s, or running concurrent
  sessions to "speed things up".
